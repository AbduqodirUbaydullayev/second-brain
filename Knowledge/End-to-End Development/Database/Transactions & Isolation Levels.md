# Transactions & Isolation Levels

> Knowledge status: 🟡 Learning

## Знаю

- Механика race condition при read-modify-write: две параллельные транзакции читают одно и то же значение, каждая считает результат от устаревшей копии, итог зависит от того, кто записал последним
- Интуиция, что доступ к изменяемому значению нужно сериализовать блокировкой

## Не знаю

- Классификация аномалий (dirty read / non-repeatable read / phantom read / lost update / write skew) — путает lost update с dirty read
- Что PostgreSQL не допускает dirty read ни на одном уровне изоляции (READ UNCOMMITTED = READ COMMITTED)
- Различия поведения READ COMMITTED и REPEATABLE READ
- EvalPlanQual: перечитывание строки после снятия блокировки на READ COMMITTED
- Serialization failure (SQLSTATE 40001) и необходимость retry на REPEATABLE READ / SERIALIZABLE
- Что момент захвата блокировки критичен — блокировать нужно в момент чтения, а не после
- Атомарный `UPDATE ... WHERE balance >= :amount` как способ устранить read-modify-write целиком
- Оптимистическая блокировка (version / `@Version`)
- `CHECK` constraint как защита инварианта на уровне данных, независимая от кода приложения

- 2026-08-22 — Уровни изоляции в ответе не фигурировали, хотя вопрос явно задавал READ COMMITTED.
